# R2 备战 · 终面（评测体系深挖 + 反问）

> 示例数据，均为虚构。一面（产品总监 滕雪）正向，剧透二面重点：评测体系怎么从 0 搭、坏案例怎么归因、跨团队怎么推动。本文件＝R2 唯一作战源，「怎么讲」部分是口语稿、可直接念。

## 0. 一页纸

终面大概率见技术 VP。考的不是复述青柠客服 agent，是能不能把它的评测方法论讲成**可复用的体系**。三个必打：评测集怎么防过拟合、坏案例三类归因、「先评测后改模型」的顺序。

## 方案一 · 评测体系怎么从 0 搭

先定义「什么算好」，再建测试集，再归因坏案例，最后才动模型——顺序错了全是返工。

> 　　我不会先调模型，先搭尺子。第一步是跟业务一起把「解决」这件事写死：未转人工、24 小时内不重复进线，才算解决——口径定不下来，后面所有数字都是各说各话。第二步建 1200 条评测集，按真实进线分布分层抽样，留一份不参与调参的盲测集防过拟合。第三步坏案例归三类：检索没召回、召回了没用对、用对了但语气崩——三类对应三套改法，混在一起就只会「再 prompt 一版」。

## 方案二 · 跨团队推动

> 　　评测体系不是产品一个人的事。算法是虚线，客服负责人手里是真实工单。我讲一个真冲突就够：上线初期客服坚持要保留「一律转人工」的兜底，跟自助解决率指标直接打架。我的做法是先用盲测集证明哪类问题 agent 比人工更稳，再把兜底缩到那几类高风险问题——用数据划边界，不是靠职级压。

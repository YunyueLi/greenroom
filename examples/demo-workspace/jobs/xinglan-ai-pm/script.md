# 星澜科技 AI 产品经理 · 面试逐字稿

> 示例稿，人物与数字均为虚构。R2（VP 面）主用版。

## 一、开场

### 题 1. 自我介绍　[每轮开场必问]

> 速查：现职 agent 战绩 → 鲸跃增长底子 → 收口到星澜评测诉求

**逐字稿（约 1.5 分钟）**

　　您好，我是林一帆。

　　我现在在青柠出行做 AI 产品，负责把客服系统改成大模型 agent。这件事我从立项带到全量：先花六周搭了一个 1,200 条真实会话的评测集，然后才让模型进来，三档灰度放量。上线到现在，自助解决率从 31% 做到 52%，客服人力成本降了 18%。

　　再往前，我在鲸跃科技做了两年半增长产品，把团队的增长实验从手工作坊做成流水线，实验吞吐从每月 3 个提到 11 个，注册转化累计提升 9.4%。

　　这两段拼起来，就是我来聊这个岗位的原因。星澜今年要把助手从问答做到代办，这件事最缺的是把「模型能不能行」变成「指标说了算」的人。评测驱动这套，我在客服场景完整跑过一遍，想在一个更大的场景再做一次。

**数字出处**
- 解决率 31%→52%，统计口径=未转人工且 24h 未重复进线（被追问时主动给口径）
- 实验吞吐 3→11，以实验平台统计为准

### 题 2. 为什么离开鲸跃？　[HR 面、业务面都问过，VP 可能再核]

> 速查：业务收敛一句话 → 想去 AI 一线 → 讲完即停

**逐字稿（约 40 秒）**

　　两个原因。鲸跃的增长业务在收敛，几条线合并，我那摊事的边界越来越小。同一时间我在内部试用了公司接的大模型客服方案，判断这个方向值得用职业生涯去押。青柠给了我亲手做的机会，我就去了。

　　回头看这个决定我挺踏实的，agent 这条线我会一直做下去。

**提醒**
- 离职只讲：业务收敛 + 想去 AI 一线，不讲赛马细节；被追问就停在「组织选择，我尊重」

## 二、项目深挖

### 题 3. 讲讲客服 agent 这个项目　[业务面必问 · R1 已讲过一轮]

> 速查：烂摊子 → 先评测后模型 → 三档灰度 → 数字 → 边界判断

**逐字稿（约 2 分钟）**

　　我接手的时候，客服机器人是按钮树，用户点三层还找不到入口，自助解决率 31%，每天两千多单转人工。

　　我做的第一个决定，是先不动模型，先搭尺子。我们花六周标了 1,200 条真实会话，按「检索错、工具调用错、兜底策略错」三类归因。这一步当时被挑战过，业务方觉得慢，我的理由是：没有这把尺子，后面每次改模型都在猜。

　　**第二步**，模型进来跑评测集，过线才上灰度。灰度分三档，5%、30%、全量，每一档守两个指标：解决率和投诉率，任何一个破线就停。

　　**第三步**是定边界。涉钱、涉安全的单子，我们主动不让 agent 接，全量转人工。这是设计出来的边界，模型能力够不够是另一回事，用户敢不敢用是这个产品的生死线。

　　结果是解决率 31% 到 52%，客服人力成本降 18%。剩下那 48%，一半是我们故意不接的高风险单，一半是真做不动的长尾，这个账我们每个月都在重新算。

**数字出处**
- 解决率数字同自我介绍；被追归因时主动讲：对照组同期解决率持平
- 「52% 怎么统计」必被追问，主动给统计口径=未转人工且 24h 未重复进线

### 题 4. 让你给星澜助手从 0 搭评测体系，怎么搭？　[R2 预测题第 1 位]

> 速查：先问清场景 → 指标分层（结果/过程/体验）→ 数据从真实会话来 → 防过拟合

**逐字稿（约 2 分钟，开头留对话口）**

　　我先确认一下：助手今年的主线是从问答到代办，那评测的主对象是「任务完成」而非「回答质量」，我按这个讲，您看对不对。

　　**第一层，结果指标**。每类任务定一个不可争辩的完成判据，订票就是订到了没有、信息对不对。这层是给管理层看的，也是给模型团队定目标用的。

　　**第二层，过程指标**。任务没完成时，断点在哪：意图理解、规划、工具调用、还是用户中途放弃。我在客服项目里用三类归因，代办场景会更细，但原则一样，坏案例必须能指到环节，修起来才有的放矢。

　　**第三层，体验指标**。任务完成但用户体感差的部分：来回确认次数、响应时长。

　　数据上我只信真实会话，造的 case 跑分再好看也不算数。冷启动可以人工标一千条量级，我上一个项目就是这个量起步的。

　　另外有个坑我想提前说：评测集用久了，模型团队会无意识地往它上面过拟合。我的做法是评测集每季度换血三成，新 case 从最近的真实失败里抽。这块我也想听听星澜现在是怎么管的。

**数字出处**
- 评测集 1,200 条（出处=评测平台后台）；「每季度换血三成」是方法主张，没说成已有战绩——别讲成数字

### 题 5. 讲一次失败　[行为题高频]

> 速查：会员改版 11 天回滚 → 错在没跑受影响分布 → 变成上线前置清单

**逐字稿（约 1 分钟）**

　　鲸跃时期我主导过一次会员体系改版，上线 11 天回滚。错误在我：改了高频用户的权益门槛，上线前只看了整体收益模拟，没跑受影响用户的分布。结果伤到的全是最核心那批人，投诉量翻倍。

　　回滚之后我做了两件事。**一**，给受影响用户逐批补偿，这个面子上难看但必须做。**二**，把「存量权益变更前必须跑受影响用户分布」写进团队的上线前置清单，放在第 1 条。后来两年这条挡下过至少三次类似的事故。

**提醒**
- 失败题讲决策错误本身，不甩锅；「挡下三次」是定性回忆，被追问就说没精确统计

## 三、反问

> 速查：汇报线核实 → 评测现状 → 边界哲学

**逐字稿（按对象选 2-3 条）**

　　一、想跟您核实一下这个岗位的汇报线和团队现状，我从不同渠道听到的版本有点出入。（双轨核对：猎头说汇报 VP，R1 说汇报总监）

　　二、星澜现在的评测体系到什么程度了，是已经有底子要我来加速，还是从 0 起？这决定我前三个月该干什么。

　　三、创始人在播客里说今年要让助手敢替用户做事。「敢」的边界您怎么定，哪类任务是今年明确不碰的？

**提醒**
- 第一条问法保持中性，别点猎头的名
